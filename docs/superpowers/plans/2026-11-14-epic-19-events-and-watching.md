# Эпик 19. События и наблюдение

Дата: 2026-11-14.

## Цель

Мика запускает сценарий, когда на компьютере что-то случилось: подключили или отключили звуковое устройство, запустили или закрыли программу, подключились по RDP или отключились, заблокировали или разблокировали компьютер, пользователь отошёл или вернулся. И умеет «подожди и скажи»: следит, пока скачается файл, завершится процесс или в окне появится фраза, и сообщает об этом. Правила и причины — в решении 0031.

## Подход

Одна служба наблюдения в `mika-tools` (модуль `observe`) раз в 5 секунд снимает состояние системы через интерфейс `Sensors` и только то, что нужно включённым сценариям и идущим слежениям. Чистая логика сценариев — модель, хранилище, сравнение снимков, пауза и пределы — лежит в `mika-core` (`triggers`) и проверяется без Windows. Сработавший сценарий становится обычной задачей ядра и проходит политику рисков, как задача по расписанию. Итог слежения Мика сообщает строкой `Remark` вида `watch`: чат, голос, уведомление Windows, Telegram.

Новых событий шины, карточек чата, зависимостей и загрузок нет. Общие файлы меняются на несколько строк, новый код лежит в новых файлах.

Работа делится на две части, которые идут одновременно: ядро и инструменты (CORE), приложение и интерфейс (UI). Общие имена закреплены заранее в контракте.

## Шаги

1. **Ядро** (`mika-core`).
   - `EventsConfig { enabled, max_per_hour }` и поле `Config::events`.
   - Модуль `triggers`: события `TriggerEvent`, действие `TriggerAction`, сценарий `Trigger`, проверка `NewTrigger::checked`, хранилище `TriggerStore` со своими таблицами `triggers` и `trigger_runs` (создаются самим хранилищем), снимок `Snapshot`, потребности `Needs`, движок `Engine` (`step` — что случилось, `admit` — пауза и пределы, `restore_hour` — запуски последнего часа из базы), текст задачи `task_text`, отметка текста `text_mark` (SHA-256) для области правила и для привязки сценария к подтверждённому тексту команды.
   - `Session::submit_task_as(shown, text)`: в чате короткая строка, модели полный текст. Ходы сессии идут по очереди (`Session::turn`), источник хода выставляется при его начале.
2. **Провайдеры** (`mika-providers`). `telegram::outgoing`: строка `Remark` вида `watch` уходит владельцу.
3. **Датчики** (`mika-tools`).
   - Интерфейс `observe::Sensors`: звуковые устройства, процессы своего сеанса, состояние своего сеанса, время без ввода, текст окна.
   - `win/sensors.rs`: Core Audio, `sysinfo` с отбором по сеансу, `WTSQuerySessionInformationW`, `GetLastInputInfo`, свой экземпляр UI Automation.
   - Свой ввод не считается вводом пользователя: `observe::sensors::OwnInput` (чистая арифметика), метка вокруг каждого `SendInput` в `win/input.rs`.
   - Три строки возможностей крейта `windows` в корневом `Cargo.toml`.
   - Подделка датчиков в `testing.rs`.
4. **Слежения** (`mika-tools/src/observe/waits.rs`). Условия, реестр `Waits` (не больше пяти, срок обязателен), проверка условия по снимку, тексты сообщений.
5. **Служба** (`mika-tools/src/observe/service.rs`). Один цикл: потребности, снимок, события сценариев с паузой и пределами, запуск задач, проверка слежений, сообщения. Шаг цикла вынесен в функцию для тестов. Перед запуском сценария: свежая строка из базы, сверка отметки команды, запуски последнего часа из базы. Пути и окна слежений смотрятся отдельными задачами и сценарии не задерживают; выключенная группа «Управление окнами» прекращает слежения за окнами.
6. **Инструменты** (`mika-tools/src/observe/`). `trigger_create`, `trigger_list`, `trigger_delete`, `wait_for`, `wait_list`, `wait_stop` с оценкой риска и проверкой аргументов в `assess`.
7. **Реестр** (`mika-tools/src/lib.rs`, `sys.rs`). Группа `events`, блок регистрации, подсказки модели, поля `Shared::triggers`, `Shared::waits`, `ToolEnv::sensors`, счётчики в тестах реестра.
8. **Связка** (`mika-gui/src/app.rs`, `mika-cli`). Заполнить новые поля, запустить службу, `Ctx::tell` — заметка в разговор и строка с голосом.
9. **Приложение** (`mika-gui/src/events_page.rs`, `main.rs`). Команды `get_events`, `set_events_enabled`, `set_trigger_enabled`, `delete_trigger`, `stop_wait`; уведомление Windows для строки вида `watch`.
10. **Интерфейс** (`frontend`). Блок «Сценарии по событию» и «Сейчас слежу» на странице «Расширения» (`settings/Events.svelte`), подписи событий (`events.ts`), метка инструментов, ключи `ru.json`, сценарии предпросмотра в `dev/mock.ts`. Карточка подтверждения сценария показывается целиком: `showsWhole` в `confirm.ts`, высота островка `confirmShape` в `island.ts`, правило в `ConfirmCard.svelte`.
11. **Документы.** Решение 0031, дизайн §5, §7, §8, §10, строка в плане по эпикам.

## Проверка

`cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `npm --prefix frontend test`, `npm --prefix frontend run check`, `npm --prefix frontend run build`.

Что проверяют тесты:
- движок: первый снимок ничего не запускает; каждое событие срабатывает на своём переходе и только на нём; сон компьютера даёт новую точку отсчёта; новый сценарий не срабатывает на том, что уже было;
- пределы: пауза, предел в день со сбросом на следующий день, общий предел в час; предел в час переживает перезапуск службы и удаление сценария;
- хранилище: сохранение, замена по имени с продолжением счёта, тот же сценарий повторно ничего не меняет, удаление и создание заново не обнуляет счётчик дня, выключатель, удаление, счётчик запусков, список запусков;
- `trigger_create`: средний риск; разные сценарии, имена и тексты команды дают разные области «всегда»; карточка показывает пределы первыми, поручение одной строкой и текст команды; замена названа заменой; тот же сценарий повторно отклоняется до вопроса; несуществующая команда и лишние аргументы отклоняются;
- служба с подделанными датчиками: сценарий отдаёт задачу с короткой и полной строкой; выключатель и пределы её не отдают; команда с изменённым текстом сценарий выключает; без сценариев и слежений датчики не вызываются; в задаче нет текста окна, а название устройства помечено как данные; зависшее чтение окна не задерживает сценарии и не запускается второй раз;
- слежения: каждое условие, срок, предел в пять, закрытое окно, окно, ставшее «слепым», — без единого чтения его текста; слова модели идут после факта; слежение, добавленное во время опроса, ждёт следующего; выключенная группа окон прекращает слежения за окнами; сетевая папка и папка другого пользователя — средний риск; диалог впереди не берётся под слежение;
- свой ввод: арифметика `OwnInput`, в том числе переполнение счётчика тиков;
- сессия: задача за ходом из Telegram не забирает его источник; сообщение из Telegram за сценарием получает источник только на своём ходу; «стоп» снимает задачу из очереди;
- интерфейс: высота островка для карточки сценария с поручением в 300 знаков;
- Telegram: строка вида `watch` уходит, вида `trigger` — нет;
- счётчик реестра: 100 инструментов.

Живые тесты по умолчанию не запускаются:
- `live_sensors`: печатает звуковые устройства, число процессов своего сеанса, состояние сеанса и время без ввода;
- ручной прогон: сценарий на запуск и закрытие Блокнота, слежение за файлом в «Загрузках», переподключение RDP; сценарии «ушёл» с паузой музыки и «вернулся» при одной минуте — второй не срабатывает от нажатия самой Мики.

## Что не делаем

- Форму создания и правки сценария в настройках.
- Действие после «подожди»: только сообщение.
- Слежения после перезапуска.
- События сети, USB, питания, файлов и заголовков окон.
- Слежение по снимкам экрана и за окнами, текст которых не виден UI Automation.
- Ответы сценария в Telegram.
- Подписку на события Windows вместо опроса.
